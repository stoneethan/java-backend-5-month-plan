# 执行机制

## 每周固定闭环

1. 周初从 [逐周任务](weekly-plan.md) 选出本周必须完成的三个证据型输出。
2. 每个学习日填写 [每日日志](../templates/daily-log.md)，只记录实际编码、测试和结论。
3. 周六完成一个可运行集成结果。
4. 周日进行 3–5 题周测，没有测试就不算完成本周。
5. 周日填写 [每周复盘](../templates/weekly-review.md)，更新 `progress.md`。

## 完成标准

一个主题只有在同时满足以下条件时才算完成：

- 能不看资料写出最小可运行代码。
- 能说明关键 API、数据流和边界条件。
- 有测试、日志或运行结果作为证据。
- 能用自己的话解释常见错误和替代方案。
- 代码已提交，文档已更新。

## 最低可行周

遇到加班、会议或运维事务时，至少保留：

- 90 分钟算法。
- 两次共 180 分钟项目编码。
- 60 分钟周测和复盘。

当周未完成内容最多顺延一周，不允许积压成两个月的大清单。

## 延期处理

| 落后程度 | 处理 |
| --- | --- |
| 少于 1 周 | 使用弹性晚补齐，不加新主题 |
| 1–2 周 | 删除管理台高级功能、可选 Reranker 和额外 Prompt 模板 |
| 超过 2 周 | 保六服务主干、租户隔离、评测、部署和面试；算法新题降到 80 道 |

不得删除的底线：Workspace 隔离、文档异步摄取、RAG 流式回答、模型降级、自动化测试、公网部署。

## 资料使用规则

- 官方文档优先于二手教程。
- 遇到卡点先写最小复现，再问 AI。
- AI 生成代码必须逐行解释并补测试后才能提交。
- 不复制课程项目，不提交无法解释的代码。
- 不追求第一次就设计完美；先完成纵向主链路，再按测试暴露的问题重构。

## Git 规则

- 一个逻辑改动一个提交。
- 提交信息使用 Conventional Commits，例如 `feat(document): add upload endpoint`。
- 不提交 `.env`、模型 Key、数据库密码和真实业务文档。
- 每个阶段至少保留一个可运行 Release。
- 重要架构取舍写入 Issue 或 ADR。
